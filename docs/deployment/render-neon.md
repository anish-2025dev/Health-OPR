# Deploying to Render with Neon PostgreSQL

```
                      ┌──────────────── Render (Singapore) ────────────────┐
  Browser ──HTTPS──▶  │  healthos-web  (static site, React build)          │
     │                │                                                    │
     └──────HTTPS──▶  │  healthos-api  (Node web service, Express)  ──────┼──TLS──▶ Neon PostgreSQL
                      │        │ private network                           │        (AWS ap-southeast-1)
                      │        ▼                                           │
                      │  healthos-redis (Key Value, internal only)         │
                      └────────────────────────────────────────────────────┘
```

All three Render resources are defined in [`render.yaml`](../../render.yaml) as a Render Blueprint.

## 1. Create the Neon database

1. Sign in at neon.tech and create a project. **Region: AWS Asia Pacific (Singapore)**, which is the same
   region as the Render services and keeps latency low.
2. Use PostgreSQL 17 to match local development.
3. Create a database named `healthos`. Don't use the `neondb_owner` role for the app; create a role named
   `healthos_app`, for example. In Phase 2 the app role will be a non-owner, so row-level security applies to it.
4. In **Connect**, copy two connection strings for that role and database:
   - **Pooled** (the host contains `-pooler`): this becomes `DATABASE_URL`.
   - **Direct** (with the pooling toggle off): this becomes `DATABASE_MIGRATION_URL`.

   Both must end with `?sslmode=require` (Neon adds it). `sslmode=verify-full` also works. The API
   refuses to start in production without TLS to the database.

5. Recommended: create a separate Neon **branch** (or project) for staging. Never copy production data
   into it.

> Neon compute scales to zero when idle. The first request after a pause can take a moment while it
> wakes. For a live clinic pilot, consider disabling scale-to-zero on the production branch.

## 2. Create the Render Blueprint

1. In the Render dashboard, go to **New → Blueprint** and connect the `health-opr` GitHub repository.
2. Render reads `render.yaml` and asks for every `sync: false` variable:

   | Service      | Variable                 | Value                                                         |
   | ------------ | ------------------------ | ------------------------------------------------------------- |
   | healthos-api | `DATABASE_URL`           | Neon **pooled** connection string                             |
   | healthos-api | `DATABASE_MIGRATION_URL` | Neon **direct** connection string                             |
   | healthos-api | `FRONTEND_URL`           | `https://healthos-web.onrender.com` (the web URL; see step 3) |
   | healthos-web | `VITE_API_BASE_URL`      | `https://healthos-api.onrender.com/api/v1`                    |

   `APP_SECRET_KEY` is generated by Render, and `REDIS_URL` is wired to the internal Key Value instance
   automatically.

3. Render subdomains depend on name availability. If Render assigns different URLs (for example
   `healthos-api-x1y2.onrender.com`), update `FRONTEND_URL` and `VITE_API_BASE_URL` to match, then
   redeploy. The web app needs a new **build** to pick up a changed `VITE_API_BASE_URL`.

4. Apply the Blueprint. On each API deploy Render runs:
   - build: `npm ci`
   - pre-deploy: `npm run db:migrate` (uses `DATABASE_MIGRATION_URL`; a failed migration stops the deploy)
   - start: `npm run start --workspace apps/api`
   - health check: `GET /api/v1/health`

## 3. Verify

```bash
curl https://healthos-api.onrender.com/api/v1/health
```

```bash
curl https://healthos-api.onrender.com/api/v1/health/ready
```

The second should return `{"status":"ok","dependencies":{"postgres":"ok","redis":"ok"}}`. Then open the web
URL; the status card should show API, PostgreSQL and Redis as `ok`.

## Plans and cost notes

| Resource       | Plan in `render.yaml` | Why                                                                                                                |
| -------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------ |
| healthos-api   | `starter` (paid)      | Free instances sleep after inactivity (slow first load at the front desk) and cannot run `preDeployCommand`        |
| healthos-web   | static (free)         | Static hosting via CDN                                                                                             |
| healthos-redis | `free`                | Enough for health checks and cache now. Free Key Value has no persistence, so upgrade before relying on job queues |

**Trying it for free first:** change the API to `plan: free`, delete the `preDeployCommand` line, and run
migrations yourself from a Codespace against the direct Neon URL:

```bash
DATABASE_MIGRATION_URL='<neon direct url>' npm run db:migrate
```

## Deploy flow

`autoDeployTrigger: checksPass` means Render deploys a commit to `main` only after GitHub CI passes.
`buildFilter` skips redeploying the API for web-only changes, and the web for API-only changes.

## Before real patient data

This deployment works for a pilot with **synthetic data**. Before any real patient or employee data:

- Phase 2 (authentication, tenant isolation, RLS with a non-owner database role) must be complete.
- Configure Neon backups/point-in-time restore retention and test a restore.
- Add custom domains with HTTPS, error tracking and uptime monitoring.
- Get legal review of DPDP Act obligations, including hosting region. Render and Neon in Singapore means
  data is stored outside India. Confirm this is acceptable for your customers and contracts.
